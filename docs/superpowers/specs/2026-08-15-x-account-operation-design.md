# X アカウント運用の設計

作成日: 2026-08-15

## この文書の位置づけ

ニュース動画生成ツールを「AI・IT ニュースを届ける SNS 運用プロダクト」に広げる。
その第1弾として **X アカウントの自動運用** を設計する。

ご依頼は実質3つのサブプロジェクトの束だった。本書は 1 だけを扱う。

1. **X 運用基盤** ← 本書
2. コンテンツ設計のブラッシュアップ（本書の生成スキーマで一部を扱う）
3. 長尺動画の再開（別途。凍結の理由が技術ではなく方針なので、決め直しが先）

## 決めたこと（前提）

| 項目 | 決定 |
|---|---|
| X の位置づけ | 動画への導線ではなく、**独立した発信の柱** |
| 投稿の型 | 単発 / スレッド / 画像カード / ショート宣伝 の4種すべて |
| 承認 | **完全自動投稿**（人の介在なし） |
| 投稿量 | 1日 3〜4テーマ + 宣伝1。月約240投稿 |
| 記事の使い分け | 動画と X の**両方**で使う。記事ごとにチャネル別の消費を記録 |
| 計測 | 最小限（1投稿につき2回だけ指標を取って記録。自動最適化はしない） |
| 長尺 | 本書のスコープ外 |

## 外部条件（実装前に一次情報で再確認する）

### X API は 2026-02-06 に従量課金へ移行した

- 新規開発者に無料枠は無い。Basic ($200/月) / Pro も新規受付終了
- 投稿の作成 **$0.015/件、ただし URL を含む投稿は $0.20/件**
- 読み取り $0.005/投稿、$0.010/ユーザー
- 2026-02 以前に作った無料枠は継続（500投稿/月、読み取り100/月）

対象アカウント（`ri.innovate.shirokuma@gmail.com`）は 2026-08 に作成したため
**従量課金前提**。X アカウントと開発者アカウントは別物で、支払い方法の登録が必要。

**この価格差が設計に直結する。** ニュース投稿に URL を貼ると13倍のコストになるため、
**リンクは YouTube 宣伝投稿だけに付ける**。ニュース投稿は出典を媒体名のテキストで示す。

概算: ニュース投稿 210件 × $0.015 + 宣伝 30件 × $0.20 = 月約 $9（¥1,400）。

### 文字数は weighted length で数える

上限 280。**CJK は1文字 = 2カウントなので日本語は実質140字。** URL は t.co 短縮で
23カウント固定。実装前に一次情報で確認する。

### OAuth 2.0 の refresh token はローテートする単回使用トークン

有効期間6か月、`offline.access` スコープが必須。開発者コミュニティに
**理由不明で失効する事例が多数**報告されている。設計はこれに耐える必要がある。

### gpt-image-2 に system prompt は無い

`images.generate` は `prompt` 1本のみを受け取る。固定の指示は
**プロンプトへの前置**として実装する（既存 `ImageGenerator._enhance_prompt` と同じ方式）。

## アーキテクチャ

### 案の比較と選択

| 案 | 内容 | 判断 |
|---|---|---|
| A | 既存 `jobs` 表を「成果物の種類」に一般化し、1つのワーカーで両方を実行 | 却下 |
| B | **X 用に別テーブル・別ワーカーを立てる** | **採用** |
| C | `jobs` 表は共有し、`kind` 列でキューだけ分ける | 却下 |

**A を却下した理由。** 動画1本は数分、X 投稿は数秒。同じキューに載せると、
時間帯を分けて連投する要件が動画生成の詰まりで崩れる。

**C を却下した理由。** 共有によってリース機構のコードを再利用できるが、
**そのリース機構は投稿側では不要**（数秒で終わる処理に15分のリースは無意味）。
得るものが無いのに、寿命も失敗の意味も違う行が1テーブルに混ざる。

**決定的な違いは失敗の意味。** ワーカーが `claim` 後に落ちると、動画は再生成で
画像クォータを食うだけだが、投稿は**同じ内容が2回公開される**。
冪等性という要件は既存のジョブ表に無く、状態機械が別物になる。

### コンポーネント

```
[既存] NewsAggregator ──┬─→ planner.plan_daily_batch ─→ jobs ─→ JobWorker ─→ Pipeline（動画）
                        │
[新設]                  └─→ post_planner.plan_daily_posts ─→ social_posts ─→ PostWorker ─→ XClient
                                     ↑                                            │
                             PostGenerator（LLM）                          MetricsCollector
                             CardVisualGenerator（LLM）                （投稿後24h / 7d に1回）
                             ImageGenerator（既存を再利用）
```

新設するモジュール。

| モジュール | 責務 |
|---|---|
| `src/social/post_generator.py` | 記事から投稿の下書きを作る（Structured Outputs） |
| `src/social/card_visual.py` | 画像カードの視覚指示を作る（Structured Outputs） |
| `src/social/x_client.py` | X API v2 の薄いラッパ。Protocol にしてテストはフェイク |
| `src/social/x_auth.py` | OAuth 2.0 + PKCE。`TokenStore` 経由で読み書き |
| `src/social/metrics.py` | 指標の取得と Blob への記録 |
| `src/jobs/post_planner.py` | 記事を選び、下書きを作り、`scheduled_at` を入れて積む |
| `src/jobs/post_worker.py` | 予定時刻を過ぎた行を投稿する |
| `src/storage/social.py` | `social_posts` の永続化 |

**投稿生成を `ScriptGenerator` に相乗りさせない。** 台本は音声タイミング同期の制約
（`segment_narrations` と `image_prompts` の要素数一致）を背負っているが、投稿には
その制約が無い。混ぜると両方のスキーマに相手の都合が入る。

動画側のコードは**記事の消費記録の一般化を除いて変更しない**。

## データモデル

### 保存先の使い分け

既存の3分割にそのまま乗せる。

| 何を | どこに | 消えたときの影響 |
|---|---|---|
| 投稿キュー（下書き・予約） | SQLite（コンテナのローカル） | 翌サイクルで作り直せる。害なし |
| **記事のチャネル別消費記録** | **Azure Files（`data/news/*.json`）** | **二重投稿する。ここが権威** |
| 自動投稿の有効/無効 | Azure Files（`data/x_posting.json`） | 意図せず停止する |
| 計測結果 | Blob（`metrics/x/YYYY-MM-DD.json`） | 蓄積が失われ分析できない |
| OAuth トークン | Blob（`tokens` コンテナ、既存） | 再認証が必要 |

**なぜ SQLite に置けないものがあるか。** ジョブ表の SQLite はコンテナのローカル
ディスク上にあり、リビジョン更新で消える（CLAUDE.md の既知の負債）。
`main` へのマージが即デプロイなので、これは日常的に起きる。

「投稿済み」を SQLite だけに持つと、**デプロイ直後に同じ記事の投稿が作り直されて
二重投稿する**。自動投稿では確実に起きるので、権威を Azure Files に置く。

### 記事の消費記録を一般化する

`NewsArticle.video_generated: bool` → `consumed: dict[str, str]`
（チャネル名 → 消費時刻の ISO 文字列）。

- `from_dict` が旧データの `video_generated: true` を `{"video": fetched_at}` に
  変換する。**移行スクリプトなしで既存の `data/news/*.json` を読める**ようにする
- `video_generated` は `consumed` を見る property として残す。`_pick_candidates` や
  既存の呼び出し元を壊さない
- 更新は必ず `_update_article` 経由。`_category_lock`（RLock）で直列化する。
  新しい更新メソッドを直接書くと「更新が失われる」問題を踏む
- 保存は既存どおり一時ファイル + `Path.replace` で原子的に行う

### `social_posts` テーブル

**1行 = 1投稿。** スレッドは `group_id` でまとめる（既存 `jobs.batch_id` と同じ手法）。

1行 = 1テーマにして下書き全体を JSON で持つ案も検討したが、**スレッドの途中で
失敗したときにどこまで出せたかが行として観測できない**ため行に割る。

| 列 | 型 | 用途 |
|---|---|---|
| `id` | int PK | |
| `group_id` | str(36) index | スレッド／同一テーマのまとまり |
| `position` | int | スレッド内の順序（単発は 0） |
| `article_id` | str(64) index | 元記事 |
| `article_title` | Text | 表示用。記事が消えても残す |
| `kind` | str(16) | `single` / `thread` / `card` / `promo` |
| `body` | Text | 投稿本文（出典表記を含む完成形） |
| `weighted_length` | int | 生成時に計算した weighted length |
| `has_link` | bool | コスト概算に使う |
| `image_key` | Text \| None | 画像カードの Blob キー |
| `status` | str(16) index | 下記の状態 |
| `scheduled_at` | DateTime(tz) index | この時刻に出す |
| `posted_at` | DateTime(tz) \| None | |
| `tweet_id` | str(32) \| None | 投稿後の ID。返信先に使う |
| `reply_to_tweet_id` | str(32) \| None | スレッドの直前の投稿 |
| `attempts` | int | |
| `error_message` | Text \| None | 画面に理由を出す |
| `created_at` | DateTime(tz) | |

インデックス: `(status, scheduled_at)`（ワーカーの検索がこの形）。

時刻は SQLite がタイムゾーンを保存しないため、**読み出し時に UTC を付け直す**
（既存 `src/storage/jobs.py` の `_as_utc` と同じ）。

### 状態機械

動画ジョブ（`QUEUED → RUNNING → SUCCEEDED/FAILED`）とは別物。

```
DRAFTED → SCHEDULED → POSTING → POSTED
                          │
                          ├→ FAILED        （API を呼ぶ前に失敗したと確実に分かる場合のみ）
                          └→ NEEDS_REVIEW  （呼んだ後に落ちた／応答不明／トークン失効）
```

- 遷移は明示的な許可表で検証する（既存 `src/models/job.py` の `check_transition` と同じ方式）
- `DRAFTED` は下書きができて予定時刻が未定の状態。`post_planner` が `scheduled_at` を
  入れて `SCHEDULED` に進める
- **`POSTING` で残った行は自動で再投稿しない。** `NEEDS_REVIEW` に移して画面に出す。
  X API に冪等キーが無いため、再試行すると同じ内容が2回公開される。
  **取りこぼしのほうが二重投稿より安全**という判断（動画ジョブは逆で3回まで自動リトライ）
- `FAILED` からの再実行は手動のみ

## 投稿の生成

### 型ごとの予算

`check_length_budget` に相当するバリデータで強制する。数値は日本語の文字数。

| 型 | 本文 | 補足 |
|---|---|---|
| `single` | 105〜125字 | `出典: <媒体名>` の表記ぶんを残す |
| `thread` | 各 100〜130字 × 3〜5投稿 | 構成は台本の `<<STRUCTURE_SPEC>>` を流用 |
| `card` | 60〜90字 | 画像1枚が主役 |
| `promo` | 70〜100字 | URL 23カウント + 動画タイトル |

**上限だけでなく下限も書く。** CLAUDE.md の実測（上限だけ指定すると145字まで
下振れし、セグメントが文の断片になった）と同じ失敗が投稿でも起きる。

### 独自解説を必須フィールドで強制する

台本の `technical_insight` / `practical_impact` と同じ理屈。スキーマの必須フィールドは
プロンプトでのお願いより強制力が強い。

- `practical_use`（必須）— **誰が、何に使えるか。** 主語を具体的に書かせる
- `why_now`（必須）— なぜ今これが起きたか

最低文字数は strip 後の長さで検証する（`Field(min_length=...)` だけでは全角空白で通る）。

### 捏造の防止

自動投稿なので、機械的な検証だけが防衛線になる。3段構え。

1. **`source_url` / `source` をモデルに渡さない。** 台本と同じ。出典の媒体名は
   コード側が `NewsArticle.source` から差し込む。渡せば捏造する
2. **数値の grounding 検証。** 生成文から数字を含むトークンを抽出し、記事本文に
   現れないものがあれば**破棄**する。1回だけ再生成し、それでも通らなければ
   その記事の投稿を諦める。列挙表現（`3つ` `2点` `1つ目` など）は除外リストで通す
3. **ハッシュタグは設定の固定セットから選ぶ。** モデルに作らせない
   （無関係なタグはスパム判定を受ける）

### 画像カード

**gpt-image-2 でイラストスケッチ風の概念解説図を1枚生成する。**

記事本文をそのままプロンプトに入れることはしない。OpenAI のガイドは
`background/scene → subject → key details → constraints` の順と、長文1段落ではなく
ラベル付きの短いセグメントを推奨している。数千字の日本語記事を投げると、モデルが
「何を1枚に描くか」を自分で決めることになり、毎回違うものが出る。

**既存パイプラインと同じ2段構えにする。**

```
記事本文 ──→ [LLM / Structured Outputs] ──→ CardVisual ──→ [固定スタイル文 + CardVisual] ──→ gpt-image-2
                                                │
                                        caption_ja は投稿本文へ
```

`CardVisual` のスキーマ。

| フィールド | 内容 |
|---|---|
| `subject` | 1枚で説明する概念を英語1文で |
| `key_details` | 描く視覚要素とその関係を2〜4個（英語） |
| `labels` | 画像に入れる短いラベル 0〜4個。**英語・大文字のみ** |
| `caption_ja` | 投稿本文に載せる日本語の1文（**画像には入れない**） |

**ラベルを英語に限る理由。** gpt-image-2 は O-series の推論を内蔵して図解と文字描画が
得意になったが、**日本語（CJK）の描画は保証されていない**。日本語の説明は投稿本文に
持たせれば確実に読めるので、画像に賭ける必要がない。

固定スタイル文（コードの定数。単一の情報源にする）。

```text
Medium: hand-drawn illustrated sketch — an engineer's whiteboard explainer
  redrawn cleanly. Loose ink linework with visible stroke ends, light marker
  fills, faint paper grain.
Palette: off-white paper ground, near-black ink, one accent (deep teal), one
  highlight (warm amber). Flat fills only — no gradients, no glossy 3D render.
Composition: a single explanatory diagram, centred, front-on flat view,
  generous margins. One idea only — no comic panels, no multi-step timeline.
Intended use: an explanatory illustration for a technology news post.
Constraints: render NO Japanese or CJK characters. No watermark, no logos, no
  UI chrome, no photorealism. Do not depict any real, identifiable person; use
  simple silhouettes if a figure is needed.
```

この後ろに `Subject:` / `Key details:` / `Labels:` を差し込む。

運用面の判断。

- **サイズは 1024x1024（1:1）。** X のタイムラインで 16:9 より縦の面積を取れて
  クロップも起きない。`gpt-image-2` の「両辺が16の倍数」制約も満たす
- **生成は下書き作成時。投稿時ではない。** ガイドに「複雑なプロンプトは最大2分」と
  あり、予定時刻に間に合わなくなる。PNG は Blob に置き、投稿時は
  `ArtifactStore.fetch()` で借りてアップロードする
- **コンテンツフィルタに拒否されたら単発ポストに降格する。** 既存の
  `ContentFilterError` は再試行しても変わらないため即伝播する設計になっている。
  画像カードが落ちてもその日の投稿は出す
- **動画生成中は画像カードを作らない**（`has_active_jobs()` を見る）。
  `gpt-image-2` のクォータはリージョン単位で上限4という律速のまま

## 投稿の実行

### 認証

X の OAuth 2.0 は Authorization Code + PKCE で**リダイレクト先が必要**。
YouTube の `InstalledAppFlow` と同じ理由でコンテナの中では実質完了できない。

**同じ運用にする。** ローカルで1回認証し、`uv run python -m scripts.push_tokens` で
保存先へ送る。`TokenStore` に `x_token` を足し、`config.token_paths` の対応表も
更新する（ローカルと Blob で名前を揃える。ずれると local ↔ blob を行き来したときに
別のものを指す）。

スコープ: `tweet.read` / `tweet.write` / `users.read` / `media.write` / `offline.access`。

**refresh token の扱いが YouTube と違う。**

- **更新したら必ず保存先へ書き戻す。** 単回使用なので、書き戻さずにプロセスが
  落ちると次回の更新ができず再認証になる。**書き戻しは投稿より先**に行う
- **失効を異常として扱わない。** ランダム失効の報告が多いため、失効時は投稿を
  `NEEDS_REVIEW` にして画面に再認証ボタンを出すだけにする。例外で落とすと
  画面を開くだけで 500 になる（`TokenStore` の既存の判断と同じ）
- **レプリカを2つ以上にすると壊れる。** 2プロセスが同時に refresh すると片方が
  無効化される。`minReplicas = 1` の前提に依存する既知の制約として記録する

### スケジュール

- `X_POST_TIMES`（例 `08:00,12:30,19:00,21:30`、JST）。**リスト型なので
  `NoDecode` が必須。** これを忘れると `.env` では通るのに実際の環境変数だと
  `SettingsError` で起動しなくなる
- `post_planner` は既存 `src/jobs/scheduler.py` に相乗りして1日1回走り、
  記事を選び、下書きを作り、`scheduled_at` を入れる
- `PostWorker` は `status = SCHEDULED AND scheduled_at <= now()` を1件取って投稿する。
  ポーリングは30秒（投稿時刻の精度は分単位で十分）
- **リースも heartbeat も持たない。** 投稿は数秒で終わる

**溜まった投稿を一気に出さない。** `scheduled_at` が `X_MAX_POST_DELAY_MINUTES`
（既定60）以上過ぎた行は投稿せず破棄する。デプロイやプロセス停止で数時間止まった
あと、復帰した瞬間に4件が連投されるとスパムに見える。

### スレッドの部分失敗

`position` 順に投稿し、`reply_to_tweet_id` に直前の `tweet_id` を入れる。
**途中で失敗したら残りは `NEEDS_REVIEW` にして自動では続けない。**
半端なスレッドは画面に出して、手で続けるか消すかを選ぶ。時間が経ってから
続きを足すと文脈が切れる。

### コストの上限

- `X_MONTHLY_BUDGET_USD`（既定 20）と単価2つ
  （`X_COST_PER_POST_USD` / `X_COST_PER_POST_WITH_LINK_USD`）を設定に置く。
  **料金は改定されるのでコードに埋めない**
- 当月の `POSTED` 行を `has_link` 別に数えて概算し、上限を超えたら投稿を止める
  （行は `SCHEDULED` のまま残し、画面に「予算上限で停止中」を出す）
- **画面には「概算」と明示する。** 実際の課金は X 側の集計なので一致を保証できない

### 停止と開始のスイッチ

完全自動なので、暴走時に止める手段が無いと取り返しがつかない。

- スイッチの実体は **Azure Files 上の `data/x_posting.json`**。
  **SQLite に置くとデプロイごとに勝手に停止する**（ローカルディスクなので消える）
- `X_POSTING_ENABLED` は「そのファイルが無いときの初期値」。**既定 false**
- 画面から開始・停止できる。一度画面で切り替えたら、以降はファイルが権威

### 計測

`MetricsCollector` が**投稿後24時間と7日の2回だけ**取る。

毎日全件を追うと読み取り課金が月 $8 を超えるが、2回なら月約 $2。
`GET /2/tweets?ids=`（最大100件/リクエスト）でまとめて取る。

結果は **Blob に日次 JSON**（`metrics/x/YYYY-MM-DD.json`）。SQLite はデプロイで
消えるため、蓄積が要るデータを置けない。

**自動最適化はしない。** データが数十件しかない時期に型や時間帯を自動調整すると
ノイズに追従して安定しない。伸びたテーマは人が見て判断する。

## 画面

### 画面の仕事が変わる

「動画を作るツール」→ **「自動で回っているものを見張る卓」**。
完全自動投稿なので、運用者の仕事は操作ではなく**出る前に気付くこと**の一点。

現状の UI（青のグラデーションヘッダー + 白い角丸カード + 絵文字）はその仕事のために
作られていない。

### 設計トークン

Tailwind v4 の `@theme` で定義し、テンプレートでは `bg-paper` / `text-ink` のような
意味のある名前を使う（hex をクラスに散らさない）。

| トークン | 値 | 役割 |
|---|---|---|
| `ink` | `#16232B` | 文字・罫線。純黒でない紺寄りのインク |
| `paper` | `#EEF1F0` | 地。製図紙の冷たい白 |
| `raised` | `#FBFCFC` | カード |
| `teal` | `#0F6E6B` | 投稿済み・主要操作 |
| `amber` | `#C97A16` | 予約済み・予算警告 |
| `vermilion` | `#B23B2E` | 失敗・要確認 |

**生成する画像カードと同じ配色にしている**（インク線 + deep teal + warm amber）。
運用者は一日中その絵を見るので、画面がそれと喧嘩しないほうがよい。
青のグラデーションは何のアプリでもあり得る既定値だった。

### 書体

**CDN を使わない制約があるので、欧文だけをベンダリングする。**

- **表示・数値: IBM Plex Sans Condensed / IBM Plex Mono。** Latin サブセットの
  woff2 を `static/fonts/` に置く（合計 60KB 程度。htmx と同じ扱い）。
  時刻・件数・金額・文字数はすべて等幅の tabular figures。
  **時刻が主役のダッシュボードなので、数字に語らせる**
- **和文: システムスタック**
  （`"Hiragino Kaku Gothic ProN", "Yu Gothic", "Noto Sans JP", sans-serif`）。
  和文 webfont は数 MB になるためベンダリングしない

### レイアウト

このプロダクトの本質は「決めた時刻に、自分では見ていない間に出る」こと。
だから画面の主役は数字のタイルではなく**1日の時間軸そのもの**にする。

```
┌───────────────────────────────────────────────────────────────┐
│ shirokuma news         ● 自動投稿 稼働中    概算 $6.20 / $20   │
├───────────────────────────────────────────────────────────────┤
│ 8/15 (土)                                                      │
│  06:30      08:00      12:30   ▎いま  19:00      21:30        │  ← 署名要素
│  ├─動画───┤ ├単発─┤   ├スレッド─┤      ├カード┤   ├宣伝─┤      │
│   投稿済     投稿済     投稿済            予約      予約        │
├─────────────────────────────────┬─────────────────────────────┤
│ 投稿キュー                       │ 記事プール                   │
│ ┌─────────────────────────────┐ │ ┌──────────────────────────┐│
│ │ 19:00  カード         236/280│ │ │ AI · TechCrunch          ││
│ │ ┌────┐ 本文がそのまま全文    │ │ │ 記事タイトル…             ││
│ │ │ 絵 │ 読める。畳まない。    │ │ │ 動画 ●  X ○              ││
│ │ └────┘ 出典: TechCrunch     │ │ └──────────────────────────┘│
│ │        [ 取り消す ]          │ │                             │
│ └─────────────────────────────┘ │ 生成済み動画                 │
│ ┌─────────────────────────────┐ │                             │
│ │ 21:30  宣伝    要確認        │ │                             │
│ └─────────────────────────────┘ │                             │
└─────────────────────────────────┴─────────────────────────────┘
```

**帯（今日の時間割）が署名要素。** 過ぎた枠は左、いまが縦線、これから出るものが右。
動画生成と X 投稿を同じ軸に載せるので、「動画生成でクォータが詰まっている時間に
画像カードを作ろうとしている」といった噛み合わせが目で見える。

### UX の判断

- **下書きは畳まない。** 運用者の唯一の仕事が「読んで気付くこと」なので、
  開かないと読めない UI では誰も読まない。140字なので全文が入る
- **文字数を常に出す**（`236/280`）。**X が数える単位（weighted length）で出す。**
  日本語の文字数で見せると直感には合うが、実際に弾かれる境界とずれる
  （日本語1字が2カウントなので、140字で上限ぴったり）。運用者が見たいのは
  「あと何文字入るか」ではなく「弾かれないか」
- **状態は色と語の二重で示す。** 色だけでは伝わらない（`予約` `投稿済` `要確認` を
  文字でも書く）
- **`要確認` は帯の上でも目立たせる。** 半端なスレッドの放置が最悪の結果なので、
  キューの下に埋めない
- **記事プールは丸2つでチャネル別の消費を示す。** `consumed` がそのまま UI になる
- **操作名を通す。** 「取り消す」を押したら通知も「取り消しました」。
  現状は `アップロード` と `submit` が混在している
- **絵文字を UI から外す。** 状態は色と語で示す。絵文字は既定のダッシュボードに見える
- **htmx のポーリングは帯とキューだけ**に絞る

### 動き

**「いま」の縦線が実時間で進む、それだけ。** `prefers-reduced-motion` では止める。
他のアニメーションは入れない（自動で動くものを見張る画面で、動くものが増えると
信号が埋もれる）。

品質の床: モバイル幅で1カラム、キーボードフォーカスの可視化、`aria-live` で
投稿完了を伝える。

**テンプレートのクラスを変えたら `npm run build:css`。** `static/css/app.css` は
生成物をコミットしているため、実行しないとスタイルが効かない。

## 設定（`config.py` と `.env.example` の両方に足す）

`tests/test_config.py` がモデルの項目と `.env.example` の記載を双方向に
突き合わせているので、**片方だけ更新するとテストが落ちる**。

| 名前 | 既定 | 用途 |
|---|---|---|
| `X_POSTING_ENABLED` | `false` | スイッチファイルが無いときの初期値 |
| `X_CLIENT_ID` | — | OAuth のクライアント ID |
| `X_CLIENT_SECRET` | — | `SecretStr` |
| `X_POST_TIMES` | `08:00,12:30,19:00,21:30` | 投稿時刻（JST）。**`NoDecode` 必須** |
| `X_MAX_POST_DELAY_MINUTES` | `60` | これ以上遅れた投稿は破棄する |
| `X_MONTHLY_BUDGET_USD` | `20` | 概算コストの上限 |
| `X_COST_PER_POST_USD` | `0.015` | 単価（改定に追随するため設定） |
| `X_COST_PER_POST_WITH_LINK_USD` | `0.20` | リンク付き投稿の単価 |
| `X_HASHTAGS` | — | 固定のハッシュタグ集合。**`NoDecode` 必須** |
| `X_POSTS_PER_DAY` | `4` | 1日のテーマ数（宣伝投稿は含まない） |

API キーは `SecretStr`。使うときは `.get_secret_value()`。

## テスト

| 対象 | 方法 |
|---|---|
| 生成スキーマ（字数予算・必須フィールド・数値 grounding） | 単体。LLM を呼ばない |
| 状態遷移の許可表 | 単体 |
| **`POSTING` で残った行を自動再投稿しないこと** | 単体。回帰として最重要 |
| スレッドの部分失敗から `NEEDS_REVIEW` に落ちること | 単体。フェイク `XClient` |
| 遅延した投稿を破棄すること | 単体 |
| コスト上限で投稿を止めること | 単体 |
| 旧 `video_generated` を `consumed` として読めること | 単体。旧形式の JSON を入力に |
| refresh token を書き戻すこと | 単体。フェイク `TokenStore` |
| weighted length の計算 | 単体。日本語 / 英語 / URL / 絵文字 |
| 実投稿の往復 | `-m live`。1件だけ投稿して削除する |
| 画像カードの生成 | `-m live`。画像クォータを消費するので既定では走らせない |

`XClient` は Protocol にして、フェイクを差し込む（既存 `JobRunner` と同じ方針）。

`tests/test_model_registry.py` の対象は AI モデルなので、X API のバージョンは
含まれない。**X API の仕様変更に気付く経路は現時点で無い**（既知の穴として記録）。

## 実装の順序

各段の終わりで動くものが増える形に割る。**投稿を有効にするのは最後**
（`X_POSTING_ENABLED` の既定が false なのはこのため）。

1. **記事の消費記録の一般化** — `consumed` への移行と旧データの読み込み。
   ここだけは既存コードに触るので、単独で入れて回帰を確認する
2. **`social_posts` と状態機械** — テーブル、Alembic のマイグレーション、
   状態遷移の許可表。投稿はまだしない
3. **投稿の生成** — `PostGenerator` と字数予算・grounding 検証。
   生成した下書きを画面で読めるところまで（投稿しない）
4. **認証** — `x_auth` と `TokenStore` への `x_token` 追加、`push_tokens` の対応
5. **投稿の実行** — `PostWorker`、スケジュール、コスト上限、スイッチ。
   **ここで初めて実際に投稿する**
6. **画像カード** — `CardVisual` とスタイル文、Blob への保存、メディアアップロード
7. **画面の作り直し** — トークン、書体のベンダリング、帯、投稿キュー
8. **計測** — `MetricsCollector` と Blob への日次記録

3 と 7 は独立しているので順序を入れ替えられる。1 → 2 → 5 の依存は固い。

## 既知の制約（実装後も残るもの）

- **レプリカを2つ以上にできない。** refresh token の同時更新で片方が無効化される。
  SQLite のジョブ表と同じ制約の列に並ぶ
- **デプロイで実行待ちの下書きが消える。** 翌サイクルで作り直せるので害は小さいが、
  その日の投稿は減る
- **コストは概算。** 実際の課金は X 側の集計であり、一致を保証しない
- **X API の仕様変更・料金改定に気付く仕組みが無い。** 単価を設定に出したのは
  追随を楽にするためだが、変化の検知はできていない
- **投稿の削除は実装しない。** 誤投稿は X の画面から手で消す
  （自動削除は、誤って正常な投稿を消す危険のほうが大きい）

## 実装前に確認する項目

1. X 開発者ポータルで従量課金の実際の条件と単価（本書の数値は二次情報）
2. weighted length の仕様（CJK = 2 カウント、上限 280）
3. `media.write` スコープとメディアアップロードのエンドポイント・課金の有無
4. refresh token のローテーション挙動を実際のトークンで1往復
